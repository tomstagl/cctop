SUMMARY: Anthropic's own guidance (code.claude.com/docs/en/best-practices, costs, context-window, prompt-caching, sub-agents, memory, goal, checkpointing; the context-engineering, writing-tools, building-effective-agents, long-running-harness and multi-agent posts; the prompt-caching and steering blog posts) plus Boris Cherny's published tips, the /insights friction taxonomy and two community token-saving lists converge on one constraint ("the context window is the most important resource to manage") and one quality lever ("give Claude a way to verify its work" – Cherny: 2–3x on result quality). From these I catalogued 41 practices; cctop's 18 rules already cover roughly 12 of them fully or partially (cache misses/expiry, runaway results, re-reads, explore-in-main, compaction churn, idle MCP, thinking share, permission waits, long foreground, pastes, chatty turns, rate pacing, subagent model, error loops, hook overhead, big prefix, no hand-off), but almost nothing on the 'better outcomes / less rework' axis: verification after edits, plan-before-multi-file-change, correction loops (/clear after two failed corrections), rewind-instead-of-correct, /btw for side questions, TDD ordering, review-before-PR, progress notes, commit cadence, mid-session model/effort switches (the most expensive avoidable cache miss), idle loops/goal check-ins re-sending full context, and CLAUDE.md feedback loops. Every one of these has an observable signal in data Claude Code already writes: transcript tool_use/tool_result ordering, `permission-mode` lines and `plan_mode`/`plan_mode_exit`/`goal_status`/`todo_reminder`/`hook_success`/`hook_blocking_error` attachments, `compact_boundary.compactMetadata` (trigger/preTokens/postTokens/durationMs), `[Request interrupted by user]` markers and `toolUseResult.interrupted`, `promptSource`, `effort`/`perTurnEffort`, image blocks in user content, `~/.claude/history.jsonl` (the only reliable record of /clear, /compact, /model, /btw, /rename, /goal, /loop – local counts: /model 75, /clear 56, /compact 18, /btw 15), `~/.claude/usage-data/{facets,session-meta}` (the /insights inputs: friction_counts keys wrong_approach/buggy_code/user_rejected_action/misunderstood_request/excessive_changes, outcome, user_interruptions, tool_error_categories, git_commits), status-line `prompt_cache` (hit ratio, misses, "likely cause: tool definitions changed"), and hook events (PostToolUseFailure, PermissionDenied, PreCompact/PostCompact compact_trigger, PreModelSwitch, SubagentStart/Stop). The right moment for most nudges is either UserPromptSubmit (before the turn: vague/short prompt, no verification target, plan mode off for a feature request, unrelated topic in a full context) or Stop/turn end (after: edits without a test run, tests green with large uncommitted diff, two corrections in a row, context past 50–60 % at a natural boundary). A minimal coach view can be built from ~12 high-confidence signals (findings P01, P03, P07, P09, P12, P13, P16, P19, P22, P27, P30, P33) with no model call.

[P01] Give Claude a check it can run after edits (tests / build / lint / screenshot) | lever=better_outcomes, less_rework | used=no | conf=high
  DETAIL: PRACTICE: every implementation turn should end with a pass/fail check Claude ran itself. WHY: 'Claude stops when the work looks done. Without a check it can run, "looks done" is the only signal available, and you become the verification loop' (best-practices); Cherny: 'give Claude a way to verify its work… it will 2-3x the quality of the final result'. SIGNAL: in the transcript, a run of Edit/Write/MultiEdit/NotebookEdit tool_use blocks followed by a `system/turn_duration` line with no intervening Bash tool_use whose `input.command` matches a test/build/lint runner (cargo test|build|clippy, npm|pnpm|bun test|run build|lint, pytest, go test|build|vet, make, tsc, eslint, mix test, gradle, mvn) and no screenshot tool (mcp__claude-in-chrome__computer action=screenshot, mcp__Playwright__browser_take_screenshot). Strengthen with `toolUseResult.stdout/stderr` (Bash) or `returnCodeInterpretation` to see the check actually passed. Stop hook input `last_assistant_message` lets a hook see the final claim. MOMENT: at turn end (Stop / turn_duration) and again at PreToolUse for `git commit` / `gh pr create`. NUDGE: 'Edited 3 files, no test/build run this turn — reply: "run cargo test and fix failures before you stop".' BENEFIT: better outcomes and less rework; the single most cited practice; converts a watched session into one that closes its own loop.
  SRC: https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work ; https://github.com/shanraisshan/claude-code-best-practice/blob/main/tips/claude-boris-13-tips-03-jan-26.md ; https://code.claude.com/docs/en/costs#work-efficiently-on-complex-tasks
  EVID: Docs: 'The check is anything that returns a signal Claude can read in the conversation: a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot'; failure pattern 'The trust-then-verify gap… Fix: Always provide verification (tests, scripts, screenshots). If you can't verify it, don't ship it.' Local transcripts (81 files): 317 Edit + 141 Write tool_uses vs 4316 Bash; Bash `toolUseResult` keys {interrupted,isImage,noOutputExpected,stderr,stdout[,returnCodeInterpretation,gitOperation]}; `stop_hook_summary` keys include stopReason, preventedContinuation, hookAdditionalContext.
  ACT: After a turn that edited files with no verifying command, show one line naming the files and the missing check, with a copyable reply ('run <detected test cmd> and fix failures before stopping'). Detect the project's test command from CLAUDE.md or from earlier Bash calls in the session.

[P02] Verification target stated in the prompt (test cases, expected output, 'what fixed looks like') | lever=less_rework, better_outcomes | used=no | conf=medium
  DETAIL: PRACTICE: include the acceptance check in the request itself ('example test cases: … run the tests after implementing'; 'write a failing test that reproduces the issue, then fix it'). WHY: 'When Claude can verify its own work, it catches issues before you need to request fixes' (costs doc); fewer correction turns. SIGNAL: user prompt text (type=user, message.content string, promptSource=typed) for an implementation verb (add|implement|fix|build|refactor|migrate) with no verification cue (test|expect|should|assert|screenshot|exit 0|verify|compare) and no @file reference (transcript `attachment` of type `file`/`directory` records @-mentions) — then, in the same turn, whether a test run occurred (P01). MOMENT: before the turn (UserPromptSubmit hook has `user_prompt`; cctop can also read the prompt line as soon as it lands in the transcript, before the first assistant line). NUDGE: 'No way to verify in this request — add a test name, expected output, or "take a screenshot and compare".' BENEFIT: less rework; docs' before/after table shows the pattern.
  SRC: https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work ; https://code.claude.com/docs/en/costs#work-efficiently-on-complex-tasks
  EVID: Docs table 'Provide verification criteria': before 'implement a function that validates email addresses' → after '…example test cases: user@example.com is true… run the tests after implementing'. Costs doc: 'Give verification targets: Include test cases, paste screenshots, or define expected output in your prompt.' Local: 721 plain prompts, p10 length 13 chars, p50 85, p90 1244; 7 `attachment/file` + 8 `attachment/directory` @-mention records.
  ACT: Pre-turn banner when an implementation prompt lacks any verification cue; offer a one-line suffix to append (or send as a queued follow-up: transcript `queue-operation` shows queueing is available mid-turn).

[P03] Visual verification for UI work (paste the design, take a screenshot, compare) | lever=less_rework, better_outcomes | used=no | conf=medium
  DETAIL: PRACTICE: for UI/CSS/HTML changes, give Claude the target image and ask it to screenshot and diff. WHY: 'Verify UI changes visually' (best-practices); Agent SDK post: screenshots verify 'layout, styling, content hierarchy, and responsiveness'; Cherny: Chrome extension is 'more token-efficient' than Playwright for frontend verification. SIGNAL: Edit/Write to paths matching \.(tsx|jsx|vue|svelte|css|scss|html)$ in a turn with no image block in any user message (user `message.content[]` type=image; 14 prompts locally) and no screenshot tool call (mcp__claude-in-chrome__computer / mcp__Playwright__browser_take_screenshot) before turn end. MOMENT: at turn end; before-turn variant when the prompt describes a visual result in words at length ('make it look…', 'align', 'spacing') without an image. NUDGE: 'UI files changed, nothing rendered — ask: "take a screenshot and list differences from the design".' BENEFIT: better outcomes; the /insights write-ups list 'Formatting Iteration Loops' (35 instances in one user's report) as a top friction category — exactly the loop screenshots close.
  SRC: https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work ; https://claude.com/blog/building-agents-with-the-claude-agent-sdk ; https://vanja.io/claude-code-insights-revealed/

[P04] Test-first ordering (failing test → fix → green) for bug fixes | lever=less_rework | used=no | conf=medium
  DETAIL: PRACTICE: for bugs, 'write a failing test that reproduces the issue, then fix it'; Anthropic's security team moved to 'asking Claude for pseudocode and guiding it through test-driven development'. WHY: prevents fixes that pass by suppressing symptoms ('address the root cause, don't suppress the error'). SIGNAL: within one task, order of tool_use: Edit/Write to a test path (test|spec|_test|__tests__) → Bash test run with is_error / non-zero (toolUseResult.stderr non-empty or returnCodeInterpretation) → Edit to a non-test path → Bash test run success. Absence pattern: user prompt contains 'bug|fails|error|broken' and the first Edit of the turn is to a non-test file with no test file touched at all. MOMENT: before the turn (bug-report prompt) and at turn end. NUDGE: 'Bug fix with no test touched — ask for a failing test first, then the fix.' BENEFIT: less rework; regression protection.
  SRC: https://code.claude.com/docs/en/best-practices#provide-specific-context-in-your-prompts ; https://claude.com/blog/how-anthropic-teams-use-claude-code
  EVID: Docs 'Describe the symptom' example: '…write a failing test that reproduces the issue, then fix it'. Case study: Security Engineering shifted from 'design doc → janky code → refactor → give up on tests' to TDD with Claude. Local: 170 `#[test]`-prefixed heredoc lines in Bash inputs show tests are frequently written via Bash heredocs, so path-based detection must also scan Write/Edit `input.file_path` and Bash `cat > …` targets.
  ACT: For prompts classified as bug reports, show whether a test file was created/edited before the source fix; nudge if not.

[P07] Plan before multi-file or unfamiliar changes (explore → plan → implement → commit) | lever=less_rework, better_outcomes | used=no | conf=high
  DETAIL: PRACTICE: use plan mode (Shift+Tab / `/plan` / `claude --permission-mode plan`) when 'the change modifies multiple files, or when you're unfamiliar with the code'; Cherny: 'Start most sessions in Plan mode'; HumanLayer: 'a bad line of a plan could lead to hundreds of bad lines of code'. WHY: 'Letting Claude jump straight to coding can produce code that solves the wrong problem'; costs doc: 'preventing expensive re-work when the initial direction is wrong'. SIGNAL (all in the transcript): `{"type":"permission-mode","permissionMode":"plan"}` lines; `attachment` type `plan_mode` {reminderType, isSubAgent, planFilePath, planExists} and `plan_mode_exit` {planFilePath, planExists:true}; `ExitPlanMode` tool_use; Agent subagent_type=Plan; files under ~/.claude/plans/<slug>.md; status line has a `plan`-derived session title on accept. Absence pattern: first Edit of a task with ≥3 distinct files edited in the turn and no plan_mode/ExitPlanMode earlier in the task. MOMENT: before the turn (prompt looks like a feature/refactor request: long prompt, verbs implement|refactor|migrate|redesign, or names ≥2 files/dirs) while permissionMode ≠ plan. NUDGE: 'Feature-sized request with plan mode off — Shift+Tab to plan first (multi-file/unfamiliar code).' BENEFIT: less rework; avoids solving the wrong problem; plan also survives compaction ('The plan Claude wrote in plan mode: re-injected from disk').
  SRC: https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code ; https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode ; https://www.humanlayer.dev/blog/advanced-context-engineering ; https://code.claude.com/docs/en/context-window#what-survives-compaction
  EVID: Docs: 'Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified.' Local: permission-mode line values across 81 transcripts: auto 1261, default 54, plan 53, acceptEdits 30; 11 plan_mode + 5 plan_mode_exit attachments; 5 ExitPlanMode tool_uses; 3 files in ~/.claude/plans; history.jsonl: /plan 4 uses.   DETAIL: PRACTICE: 'If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches.
