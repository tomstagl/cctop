See what Claude Code is doing — live, in a pane beside it.

Claude Code shows you the conversation. cctop shows you what is underneath it: how full the context is and when it will be compacted, what each turn costs and why, how close you are to your usage limit, what the model is waiting on right now, which tools are filling the context — and one concrete change to make about it. Live, next to your session, without touching it.

  • Opens with/cctop — docked inside Claude Code when the build allows it, otherwise as a split of your terminal beside it. One command; it decides.
  • Runs intmux, zellij, WezTerm, Kitty, iTerm2 — or no multiplexer at all in the docked panel.
  • ReadsWhat Claude Code already writes under ~/.claude, plus the process tree. It changes nothing about your session.
  • SendsNothing. No account, no telemetry, no model call.
  • Installbrew install tomstagl/tap/cctopor cargo install cctop · then claude plugin add tomstagl/cctop and type /cctop

Five questions you ask a Claude Code session, answered while it runs

  • Why did that turn take so long?

    The Turn panel splits the wait into model time, the tool that ran, the hooks that fired, and how long the model sat waiting for you to answer a permission prompt.

    Panel 4 · Turn

  • Why is this session so expensive — is the cache even working?

    Tokens & Cost shows every token by price class and the cache-hit ratio. Below 80 % something is rewriting the prefix on every turn; the Advisor names the usual culprits.

    Panel 2 · Tokens & Cost · Advisor A01

  • Will I hit my limit before it resets?

    Limits draws the 5-hour and 7-day windows, the countdown to each reset, and a forecast from the last half hour of use — including whether you'd run out first.

    Panel 3 · Limits

  • What is filling up my context?

    Tools shows how many tokens each tool pushed into the context and names the single largest results. Files flags the reads that brought nothing new. Context forecasts the next compaction.

    Panel 5 · Tools · Panel 7 · Files · Panel 1 · Context

  • Fine — what should I change?

    The Advisor turns what it sees into one recommendation at a time: the evidence, the change, and what it saves per turn. Eighteen rules, no model call. Ask your session about any of them in plain words.

    § 4 · The Advisor

§2The dashboard, annotated See alsoEach panel has its own page with every reading explained: the panel guide.

One page, nine panels — and what each one is for

The numbers in the frame titles are the panel numbers: the digit that shows or hides a panel, the number the guide uses, and the number the docked view carries. Below the figure, what each panel tells you and what you would do about it.

  • top

    Header the session at a glance

    ● BUSY means Claude is working, IDLE means it is your move, WAITING means a permission prompt is open, ENDED means the process is gone. Then the turn number, how long this turn has run, what the model is waiting on right now (▶ Bash 0:48), the folder and branch (* = uncommitted changes). The second line: permission mode, effort level, plan, session age, cost so far, and the Claude Code process's CPU and memory.

    DoWAITING and you didn't notice a prompt? Look at the session — nothing happens until you answer it.

  • 1

    Context

    How much of the model's window is in use. The gauge fills as the conversation grows; the figures split it into the fixed part (system prompt, CLAUDE.md, tool definitions — paid on every single turn), your messages with their tool results, and what is still free. The trend line shows the growth per turn and forecasts when Claude Code will compact — summarise — the history.

    DoAt "autocompact in ~3 turns", finish the step you are on and write a short hand-off note. When the fixed part is a quarter of the window, trim CLAUDE.md and disable MCP servers this project doesn't use.

  • 2

    Tokens & Cost

    Where every token went, by price: cache read (cheap, a tenth of the input price), cache write (dear — paid whenever the cached prefix changed or expired), fresh input (full price, usually a paste), output, and the share of output that was thinking. Then the cache-hit ratio, the session's cost and its burn rate per hour, and a sparkline of cost per turn.

    DoA hit ratio under 80 % means something is changing the prefix every turn — a hook or status line that prints the time is the usual suspect. A jump in burn rate is the moment to decide whether to keep going at that pace.

  • 3

    Limits

    Your account's rolling 5-hour and 7-day usage, the countdown to each reset, and — from the last thirty minutes — whether you would run out before the reset. These are account-wide: other sessions and subagents draw from the same pool.

    Do"exhausted in 2h 05m, after reset ✓" is fine. Projected before the reset? Move exploration and summaries to cheaper subagents, or pause the heavy work until the window clears.

  • 4

    Turn

    What this turn is doing right now: time elapsed, how many round-trips to the model, time to the first token and output speed, the tool that is running and for how long, how much time hooks added, and how long the model waited for a permission answer.

    DoA long ▶ Bash is a build or test suite in the foreground — run those in the background. Long permission waits: allow that tool pattern in your settings. Heavy hook time: make the hook asynchronous or narrow what it matches.

  • 5

    Tools

    Per tool: calls, errors, the typical (p50) and worst-case (p95) duration, how long since it was last used, and how many tokens its results pushed into the context. Below the table, the single largest results by name.

    DoStart with the biggest tokens → ctx entry — one oversized ls -R or a re-read file usually explains most of the growth. Narrow the command, or hand the exploration to a subagent that returns a summary. The same tool erroring repeatedly: interrupt and give the fix yourself.

  • 6

    Agents & MCP

    Subagents — ◐ running, ✓ done, ✗ failed — with their task, runtime, tokens and model. MCP servers with process id, memory, call count and idle time. Background commands and their task numbers.

    DoA server with no calls and a long idle time still costs its tool definitions on every turn — disable it for this project. An Opus subagent doing search or summary work: point it at Sonnet or Haiku.

  • 7

    Files

    Every file the session read (R), edited (E) or wrote (W), the lines added and removed, and a ⚠ wherever a file was read three or more times without changing in between.

    DoSkim it before you commit. A ⚠ re-read put the whole file into the context again for nothing — ask for a narrower read, or for the model to keep notes.

  • 8

    Events

    The raw timeline every other panel is built from: tool calls starting and finishing, hooks firing, permission prompts opening and closing, compactions, and notes cctop records itself — such as "rate-limit 5h crossed 60 %".

    DoFind the moment a turn went slow or expensive, then open the numbered panel with the detail behind it.

  • 9

    Advisor

    One recommendation at a time, ranked by what it saves: the evidence it found, the change to make, and the estimated saving per remaining turn. n shows the next one, Enter the explanation.

    DoMake the change, or ask your session "why is my cache hit ratio low?" — the bundled skill answers from the same numbers.

  • keys

    Key line

    ? help · 1–9 show or hide a panel · Tab focus the next panel · s sort · f filter · p pause · t next theme · a ask · L switch session · q quit — which never touches the session.

§4The Advisor All 18 rulesWhat triggers each one and what to do: the Advisor reference.

One recommendation at a time, with the evidence

The Advisor watches the same numbers the other panels show and speaks only when a rule fires on this session's own evidence: what it found, the change to make, and what that change saves for the rest of the session. It ranks by the saving and shows the top one. Eighteen rules, all deterministic — no model call, no network. Three from real sessions:

▸ `Bash ls -R` pushed 4.4k tokens into context, 2×
Pipe through `head -50`, use Glob/Grep, or ask a subagent for a summary. ~8.8k/turn · A03
▸ Prompt cache expired before turn 12
Batch your questions or keep the session warm; each cold turn re-writes the whole context (TTL 1 h on this session). ~396k · A02
▸ mcp:playwright has had no calls for 42:00
Disable it for this project (.mcp.json) or rely on deferred tool loading. ~3.1k/turn · A07

You don't have to read the panel to use it. Ask the session in plain words — "why is my cache hit ratio low?", "what is filling my context?" — and the bundled cctop-insights skill answers from the same numbers, with one change to make.

§5Two ways to see it Not sure which you got?cctop pane status lists every prerequisite and the fix for each.

/cctop picks one. It never asks you to choose.

Docked panel

Inside Claude Code, above the prompt

On a Claude Code build with function hooks enabled, the dashboard docks inside Claude Code itself, drawn in its own frame and colours — no multiplexer needed. Six views: Overview (header and panels 1–4), then Tools, Agents, Files, Events and the Advisor. Click a view name in the top row, or give the pane the keyboard with ctrl+x Tab.

Terminal split

Beside Claude Code, in your terminal

Everywhere else, /cctop opens the full nine-panel dashboard as its own process in a right-hand split of tmux, zellij, WezTerm, Kitty or iTerm2 — the view in Fig. 2. You keep working on the left. It needs 40 columns; 45 % of a 132-column window gives 59, which fits the narrow layout.

If neither can attach, /cctop prints exactly what is missing and how to fix it — or run cctop run --session <id> by hand in a second terminal.

§6Install & attach Undocctop uninstall restores your settings from the backup it made.

Four lines, then /cctop

brew install tomstagl/tap/cctop           # currently v0.2.0; or: cargo install cctop
claude plugin marketplace add tomstagl/cctop
claude plugin install cctop               # adds /cctop and cctop-insights
/cctop                                     # opens the dashboard: panel or terminal split

Optional: exact rate limits and tool timings

cctop install wraps your status line with a tiny shim and registers itself for Claude Code's hook events. It shows you the diff of ~/.claude/settings.json, backs the file up to ~/.cctop/backups/, and asks before writing anything. With it, the Limits panel shows your real rate limits and the timings drop their ≈. Without it, every panel still works from the transcript alone.

§8What it reads, what it writes

Local only

cctop reads what Claude Code already writes under ~/.claude — the session list, the transcript, hook events — and looks at the process tree for running commands and MCP servers. It writes only under ~/.cctop and ~/.config/cctop. It sends nothing over the network and never changes your session.

Cost figures on subscription plans have no per-token bill behind them; cctop shows what the same usage would cost at API list price, marked ≈, so a session can still be compared with another.
